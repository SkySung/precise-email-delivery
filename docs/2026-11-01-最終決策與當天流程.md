## 朋友 2025 年的信件分析

### 他寄出的那封（寄件備份原始檔）

- `Date: Sat, 1 Nov 2025 11:00:00 +1000` ＝ 台灣 **09:00:00 整**（+1000 是澳洲東部；他現在在愛爾蘭，所以介面顯示 01:00，一致）。
- HTML 是 `<div dir="auto">`：**Gmail 手機 App** 的特徵。我們 12 封網頁版量測信全是 `dir="ltr"`。
- 他說是 59:5x 按下，`Date` 卻是 09:00:00。可能原因：
  1. （最可能）手機 App 由伺服器在取消傳送等待結束、真正送出時才蓋 `Date`；
  2. 按下的秒數記憶有誤；
  3. 手機時鐘偏快（機率低，手機走網路校時）。
- 這是寄件備份，沒有 `Received`／`X-Received`，**無法得知實際進對方信箱的時間**。
- 我們「網頁版 `Date` = 按下當下本機時間」的結論只適用桌面網頁版，**不受這封信影響**。

### 承辦人的回函（候補成功通知，2025-11-28）

- `Date: 13:22:42 +0800`，第一個 `X-Received` 13:22:54.498 → 相差約 **12.5 s**，與我們量到的網頁版 Δ2（11.2～13.2 s）一致：承辦人用桌面網頁版 Gmail，`Date` 是按下當下。
- 是 BCC 群發的新信，不是回覆原信，沒有引用行，無法反推朋友那封的抵達時間。

### 對策略的影響

- 朋友的信 `Date` 與顯示時間都在整點，看起來完全沒有提早，**仍然是備取**（後來候補成功）。
- 推論：400 名額很可能在**整點後最初幾秒內**就排完，決勝在整點後幾秒內的抵達先後 → API 的 1～2 s 抵達更有價值。
- API 策略不變。

### 嘗試過但沒用的方法

- Gmail 的 MIME boundary（`000000000000` + 16 hex）確實隨時間遞增，但用已知時間的信回歸後殘差約 ±20 s，無法分辨 59:5x 與 00:00，放棄。

- 排程在背景執行看不到畫面，也跳過了「核對內容後輸入 `yes`」這道防呆，所以正式信由人在 macOS「終端機」App 前啟動。

- Ctrl+C：`uv`、`python`、`caffeinate`（以 `-w` 監看腳本 pid）全部結束，實測無殘留 process；並依時機提示：
  - 發射前：信尚未送出，可重新執行；
  - 送出途中：信可能已送出，先看寄件備份；
  - 已送出後：不要再寄。
