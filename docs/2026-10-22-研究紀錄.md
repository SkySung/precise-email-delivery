## 1. 實驗

### 1.1 API 演練（`send_precise_mail.py --rehearse`，週四 00:02）

| 項目 | 時間 |
|---|---|
| 目標 T0 | 00:02:00.000 |
| 實際發射 | 00:01:59.998（T0 −2 ms），API RTT 523 ms |
| A 寄件備份 / B 收件匣 `internalDate` | 00:02:00 |
| B 實際進信箱（`X-Received`） | 00:02:02.046（+2.05 s） |

本機時鐘偏差 +120 ms（四台 NTP 伺服器一致），腳本已自動補償。

### 1.2 網頁版延遲（`web_probe.py -n 5`，週四 00 點，取消傳送 = 5 秒）

| 輪 | 按下（標準時間） | `Date` | 進信箱 | Δ2 |
|---|---|---|---|---|
| 1 | 00:04:28.974 | :28 | 00:04:40.885 | 11.91 s |
| 2 | 00:05:20.749 | :20 | 00:05:32.989 | 12.24 s |
| 3 | 00:06:11.996 | :11 | 00:06:23.613 | 11.62 s |
| 4 | 00:07:03.604 | :03 | 00:07:15.346 | 11.74 s |
| 5 | 00:07:54.069 | :53 | 00:08:05.764 | 11.69 s |

平均 11.84 s，標準差 0.25 s。≈ 5 s 取消傳送 + 約 6.8 s 伺服器端（API 全程只要約 2 s）。
5 輪的按下時間都落到 Python 端時間戳（`click_src=py`），頁面內 JS 按鍵監聽沒有觸發。

### 1.3 新確認的 Gmail 規則

- **網頁版的 `Date` 標頭用寄件端電腦的時鐘**，不是 Google 伺服器的時鐘。第 5 輪在標準 :54.069 按下，本機時鐘慢 122 ms → 本機 :53.947 → `Date` :53；5 輪全部符合。API 的 `Date` 則是 Google 接受的時間。
- **回信引用行（「X 於 … 寫道」）用的是收件端的進信箱時間，精度到分鐘。** 第 5 輪 `Date` 00:07:53、進信箱 00:08:05，收件人回信的引用行寫「上午12:08」。回信內容不含收件端毫秒時間戳，精確秒數只能從收件人信箱的 `X-Received` 取得。
- Gmail「取消傳送」選項只有 5 / 10 / 20 / 30 秒，**最小 5 秒，無法關閉**。

### 1.4 修正

- `web_probe.py`：Gmail 啟用 Trusted Types，Playwright `wait_for_function` 的字串 eval 會被擋；改成在 Python 端輪詢 `page.title()`。

## 3. 策略分析

兩個未知數：
- **J**：承辦人判斷「早寄」看的是抵達時間，還是寄件端時間（`Date`）
- **C**：第 400 封有效信在 09:00 後幾秒抵達

### 證據對 J 的指向

| 證據 | J = 抵達時間 | J = `Date` |
|---|---|---|
| 2020「9 點準時寄 → 提前無效」 | 網頁版需時鐘快 12 秒以上才會早到，不太可能 | 時鐘快 1 秒就會發生 |
| 2026「`Date` 8:59」沒進前 400 | 他和其他「剛好 9:00」的人時間相近，那些人都上了，有點奇怪 | 被判早寄，說得通 |
| 朋友：`Date` < T0、抵達 +5～10 s、候補 | 需要 C < 5 s 才說得通 | 被歸為早寄，說得通 |
| Gmail 介面全部顯示抵達時間 | 支持 | 需假設承辦人用其他客戶端或程式處理 |

三筆行為證據都偏向「看 `Date`」，或至少排除不了這種可能。朋友等了一個月才收到候補通知，跟一般候補時程吻合，不能當作「早寄被撈回」的證據。

### 證據對 C 的指向

2020 年度：抵達約 +10～17 s 落在第二批，推估 C ≈ +20～30 s。2026 年度：網頁版「9:00」寄出的人分布在第四批前後，推估 C ≈ +10～15 s。朋友那筆只有在 J = 抵達時間時才代表 C < 5 s。

### 決策矩陣

| 世界 | A：API 在 T0 發射（`Date` ≥ T0，抵達 +1.5～2.1 s） | B：API 提前約 1.3 s 發射（`Date` 08:59:58，抵達約 +0.5 s） |
|---|---|---|
| J = `Date` | ✅ 比所有 `Date` ≥ T0 的網頁版／App 使用者早約 10 s | ❌ 全部歸零 |
| J = 抵達時間，C ≈ +10～15 s | ✅ | ✅（多出的 1.5 s 沒有用處） |
| J = 抵達時間，C ≈ +5 s | ✅（約第 150 名） | ✅ |
| J = 抵達時間，C < 2 s | ❌ | ✅（沒有資料支持這個世界） |

**結論：採用 A（API 在 T0 整發射）。** `Date` 由 Google 伺服器蓋，不受本機時鐘影響，兩種判定方式都能通過。
不建議在 T0 −0.1 s 微調（d1 最小觀察值 0.21 s）：收益約 0.1 s，`Date` 卻有機會落到 08:59:59。

### 其他寄信方式評估

| 方案 | 抵達 | `Date` | 風險 | 結論 |
|---|---|---|---|---|
| Gmail API 在 T0 發射 | +1.5～2.1 s | Google 伺服器蓋 | 極低，已實測 | **採用** |
| `smtp.gmail.com:587` XOAUTH2，卡住 DATA 結尾到 T0 | 約 +1.3～1.9 s（只省 d1 中約 0.2 s 的 HTTP 上傳與處理） | 程式自己填，依賴本機時鐘 | 低，但要新寫程式並實測 | 收益在 C ≈ +5～15 s 下不影響結果，不做 |
| 自架程式直連 Gmail MX（卡住結尾） | 可能 +0.3 s 以內 | 程式自己填 | **高**：家用 IP 多封鎖 port 25 / 列入 PBL；以 gmail.com 寄件人從非 Google IP 投遞 SPF 失敗、沒有 Google DKIM，會被拒收或進垃圾郵件 | 不做 |
